# Phase 3.3 — DTOs, Validation and Error Model

**Status:** LOCKED
**Lock Rule:** This baseline is the binding contract reference for subsequent API phases. Material changes require an explicit revision/decision.  
**Depends on:** Phase 3.1, Phase 3.2, ADR-011, ADR-012

## 1. Contract Position

Phase 3.3 turns the Phase 3.2 command/query catalog into stable transport contracts without exposing domain entities or database schemas.

The contract has four layers:
1. Request DTO — client intent and allowed input.
2. Application validation — shape, format, authorization context and policy preconditions.
3. Domain validation — business invariants inside the owning transaction.
4. Response DTO — committed business result or explicit asynchronous/pending state.

Client-supplied tenant, organization, branch, warehouse and device identifiers are never trusted as authorization scope.

## 2. Common Request Metadata

Required/conditional headers:
- Authorization — required.
- Idempotency-Key — required for replayable mutations.
- X-Correlation-ID — optional; generated by server if absent.
- If-Match — optional where conditional concurrency is exposed.
- X-Device-ID — conditional for registered POS operations.

Where JSON concurrency/provenance metadata is needed:
{
  "expected_version": 7,
  "client_operation_id": "uuid-v7"
}

expected_version and Idempotency-Key are different controls.

## 3. Common Success Envelope

{
  "data": {},
  "meta": {
    "correlation_id": "uuid-v7",
    "idempotent_replay": false,
    "server_time": "2026-10-06T12:00:00Z"
  }
}

A replay returns the original committed result with idempotent_replay=true and creates no second business effect.

Query collections use:
{
  "data": {
    "items": [],
    "next_cursor": "opaque-cursor",
    "has_more": true
  },
  "meta": {
    "correlation_id": "uuid-v7",
    "server_time": "2026-10-06T12:00:00Z"
  }
}

## 4. Error Envelope

{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "The requested quantity is not currently available.",
    "details": {
      "product_id": "uuid-v7",
      "batch_id": "uuid-v7"
    },
    "retryable": false
  },
  "meta": {
    "correlation_id": "uuid-v7"
  }
}

code is stable and machine-readable. message is localizable. details contains only endpoint-safe information. Never expose SQL, stack traces, credentials, provider secrets or cross-tenant data.

## 6. Validation Order

1. Authentication.
2. Authorization and trusted scope.
3. Request schema/field validation.
4. Idempotency lookup and canonical-request comparison.
5. Resource existence.
6. expected_version/concurrency check.
7. Configuration/policy preconditions.
8. Domain invariants inside the owning transaction.
9. Commit.
10. Post-commit asynchronous work.

## 7. Field Conventions

- IDs: UUID v7 unless explicitly documented otherwise.
- Timestamps: RFC 3339 UTC.
- Money: decimal strings with currency-specific precision; binary floating point prohibited.
- Quantity: decimal strings with configured unit precision.
- Currency: uppercase configured code.
- Codes/enums: uppercase stable codes; clients should tolerate additive values.
- Cursor: opaque.
- Server-generated IDs are not client-supplied unless explicitly defined as provenance identifiers.

## 9. Payment DTO

{
  "method_code": "BANK_TRANSFER",
  "amount": {
    "value": "12500.00",
    "currency": "SDG"
  },
  "verification_mode": "MANUAL",
  "client_payment_reference": "optional",
  "note": "Optional"
}

Payment responses keep separate axes for payment status, verification status and evidence status. A screenshot is evidence only. Manual confirmation is an attributed business decision. API verification is returned only after a trusted provider adapter result.

## 10. Evidence DTO

{
  "evidence_type": "TRANSFER_NOTIFICATION_SCREENSHOT",
  "upload_reference": "server-issued-upload-reference",
  "captured_at": "2026-10-06T12:00:00Z",
  "note": null
}

Binary upload is a separate bounded flow with content-type/size validation, malware scanning, access control and retention. Payment JSON stores references, not large base64 images or storage credentials.

## 13. HTTP Status Rules

| HTTP | Use |
|---:|---|
| 200 | Successful query or non-creation command |
| 201 | New durable resource created |
| 202 | Accepted asynchronous operation with no final result yet |
| 204 | Successful command with intentionally empty body |
| 400 | Malformed HTTP/request syntax |
| 401 | Authentication required/invalid |
| 403 | Authenticated but forbidden |
| 404 | Authorized resource absent/undiscoverable |
| 409 | State, concurrency, idempotency or durable business conflict |
| 422 | Semantically invalid request/business rule |
| 429 | Rate limited |
| 500 | Unexpected server error |
| 503 | Temporary infrastructure/provider unavailability |

HTTP 200 must never be used to hide a failed business operation.

## 14. Idempotency Semantics

1. Client sends a unique Idempotency-Key.
2. Server binds it to actor/device scope and operation.
3. Server stores a canonical request fingerprint.
4. First successful commit stores result metadata.
5. Same key + same canonical request returns the original result with idempotent_replay=true.
6. Same key + different request returns IDEMPOTENCY_CONFLICT (409).
7. A failure before durable acceptance can be retried with the same key.
8. External provider calls use their own idempotency/reference mechanism where supported.

Idempotency records need a documented retention period sufficient to prevent financial/inventory duplication during plausible retries.

## 15. Optimistic Concurrency

Where expected_version is required:
- client sends the last observed aggregate version;
- command succeeds only when current version matches;
- success increments the version;
- stale version returns CONCURRENCY_CONFLICT (409);
- client re-reads/reconciles instead of blindly overwriting.

Offline device/aggregate sequence mechanisms are additional controls, not replacements.

## 16. Offline/Sync Response Semantics

Offline-capable commands distinguish business status, local durability and sync status.

Example:
{
  "data": {
    "sale_id": "uuid-v7",
    "status": "COMPLETED",
    "sync_status": "PENDING"
  },
  "meta": {
    "correlation_id": "uuid-v7",
    "idempotent_replay": false
  }
}

COMPLETED locally never implies cloud synchronization completed.

## 17. Minimum Contract Tests

- malformed body → 400;
- missing/invalid authentication → 401;
- unauthorized scope → 403;
- missing authorized resource → 404;
- invalid semantic input → 422;
- stale version → 409 CONCURRENCY_CONFLICT;
- same idempotency key + same request → original result, no duplicate;
- same key + different request → 409 IDEMPOTENCY_CONFLICT;
- insufficient stock → 409;
- expired batch → 422;
- missing cash session → 422;
- async verification accepted → 202;
- provider unavailable → 503;
- sync conflict → 409;
- screenshot evidence never implies API verification.

## 18. OpenAPI Gate

Phase 3.3 establishes the conventions required for OpenAPI. Final endpoint schemas, examples and authorization matrix are reconciled in Phase 3.4 before implementation authorization.

OpenAPI must document operationId, DTO schemas, required headers, security, common errors, pagination, idempotency, concurrency, and key cash/Bankak/manual/evidence/external-verification/offline examples.
